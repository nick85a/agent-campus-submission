# 05 我的复盘

我将这次项目中的确认边界、保存真实性和对话恢复作为复盘重点。实现过程使用了 AI 辅助；下面记录我的业务考虑、手工验证中发现的问题，以及从实现和测试结果中得到的技术认识。

## 我认为最难的问题

我最关注确认与保存之间的时间差。19:00在提出建议时可用，并不代表用户同意后仍可用。因此，我要求同意记录绑定素材、建议版本、规则和具体时段，并在保存前重新检查占用。更换占用时段的测试用于验证模型会重新选择动作。

我认为另一个关键问题是区分“模型说成功”和“数据库已经保存”。项目根据 SQLite 的实际记录生成业务结果，并在 INSERT 后注入异常验证回滚。我用保存失败、重复提交和最终草稿数量检查这条边界，自动化实现和核对使用了 AI 辅助。

我在手工聊天中发现，保存业务任务并不等于保留完整对话。模糊输入曾使确认丢失，重启后也曾无法继续 M06。根据这些反馈，项目通过 AI 辅助改为复用 Pi AgentSession、持久化原生历史，并把当前业务任务与 Pi 会话关联恢复。

## 我的学习与收获

1. 我认识到 SDK 和模型协议需要按实际接口验证。Pi 的消息内容可能是文本块数组，不能直接按字符串处理；本地协议测试替身只能证明接入协议，不能证明真实模型效果。
3. 我认识到幂等不能只返回缓存。已有草稿再次处理时，仍需复核资料、规则和占用，并区分本轮保存与返回已有记录。
4. 我认识到预算限制和恢复需要一起设计。大批次耗尽预算后，已完成项应经过复检后复用，让剩余素材继续处理；超限必须明确返回未完成。
5. 我区分了业务断言、Pi 工具循环、协议测试替身和真实模型决策四类证据。我运行了11场景真实模型验证，但一次通过还不能代替多次一致性统计。
6. 我认为观测应独立于工具实现，因此要求通过 `pi.on` 采集生命周期。工具在 SDK 层正常返回，也可能携带业务失败，需要结合返回体判断，并用 callId 关联开始和结束。
7. 我认识到状态修改需要明确入口。审核通过、具备保存条件、正在保存和保存成功是不同状态；事务回滚时不能留下虚假的成功迁移。
8. 我认识到确认需要绑定完整建议。时间同意和风险接受各自独立，旧时段的同意不能自动用于新建议，禁止性风险也不能被确认豁免。
9. 我认为统一业务命令能减少入口差异。CLI、Pi 工具和评估脚本共用校验，模型不能通过参数将自己声明为可信操作者。
10. 我从真实轨迹中看到工具说明会影响决策质量。资料源枚举和候选排序需要明确；“安全暂停”与“建议符合偏好”应分别判断。
11. 我在手工输入中验证了聊天的确认边界。假设、条件句和错字不能直接产生批准，半点或截止时间也不能被擅自改成整点。
12. 我要求业务聊天与运行观测分开。用户回复展示审核、风险、建议、确认和草稿状态，工具参数与 Trace 保留在后台。重复提交和失败重试也需要明确区分。
13. 我认识到业务状态与模型记忆需要分别保存、关联恢复。对话历史帮助理解“刚才那条”，实际批准与保存仍由业务状态和版本校验决定。

## 我的下一步

我计划在固定数据上重复运行资料不足、风险、冲突和保存失败场景，统计一致性，并亲自复核确认边界和关键代码。

我会补充个人独立修改与验证记录，以及实际净投入时间。对于真实素材接入、带版本的外部排期、身份认证、草稿改排和撤销、时段保留以及音视频审核，我会先明确新的业务规则与验收，再扩展实现。
